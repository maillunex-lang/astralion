# Правила работы ИИ с «Астралион: Наследие звёзд»

## Минимальный контекст

1. Прочитать этот файл и [PROJECT_STATE](docs/development/PROJECT_STATE.md).
2. Если нужен выбор задачи — открыть [ROADMAP](docs/development/ROADMAP.md).
3. Открыть только соответствующий stages/*.md и текущий tasks/TASK-ID.md.
4. Проверить обязательные зависимости, назначить владельца и ветку; читать только связанные исходники.
5. При недостатке контекста найти исходный ID в [индексе](docs/development/DECISIONS_INDEX.md)
   и прочитать нужный раздел закреплённого GAME.md по ссылке.

Не перечитывать весь GAME.md автоматически в каждой сессии.
Исключения: первичная индексация, масштабное изменение архитектуры, противоречие
или недостаточность извлечённого контекста. Повторный полный аудит должен иметь причину.
Важные правила продублированы в [README системы](docs/development/README.md).

## Источник и границы

- GAME.md — источник утверждённых решений; не сокращать, не менять и не копировать целиком.
- Сохранять оригинальные ID, канонические реплики, ограничения и исключения.
- Новые обязательные механики не придумывать. Техническое предложение обозначать отдельно.
- Противоречие записать в RISKS.md; затронутую часть заблокировать, не выбирать правило произвольно.
- При изменении main источника сравнить закреплённый SHA и затронутые ID до обновления индекса.
- Все новые документы писать по-русски. Не удалять чужой код/документы и не переписывать историю.
- Задание на дорожную карту не разрешает реализацию игры или инфраструктуры.
- Не устанавливать зависимости без необходимости; не выполнять опасные миграции и production-операции.
- Секреты, токены и ключ APK не хранить в Git/логах/TASK-файлах.

## Работа над задачей

- Канонические ID, статус и зависимости — таблица в stages/*.md; TASK — конкретный рабочий пакет.
- До кода заполнить цель, allowlist/denylist, владельца, ветку, команды и критерии TASK.
- Уточнить текущий HEAD и повторить только проверки, актуальность которых могла измениться.
- Код ≠ сборка ≠ наличие тестов ≠ успешные тесты ≠ подтверждённый runtime.
- Статусы: TODO, IN_PROGRESS, PARTIAL, BLOCKED, DONE, UNKNOWN.
- UNVERIFIED — отметка отдельного доказательства, не дополнительный статус задачи.
- DONE допускается только при успешных обязательных проверках с командой/сценарием, SHA и результатом.
- Если реализация есть, но проверок нет — PARTIAL/UNKNOWN; проваленный обязательный тест запрещает DONE.
- Если задача велика — выделить дочерние ID до кода; не переименовывать существующий родительский ID.

## Несколько агентов

- Отдельная ветка или worktree на пакет: `task/<id-в-нижнем-регистре>`.
- В TASK указать владельца и базовый SHA. Никому не писать в чужой worktree.
- Не назначать пересекающиеся allowlist одновременно. Общий контракт сначала интегрирует один владелец.
- stages, ROADMAP, PROJECT_STATE и CHANGELOG — общие файлы; их интегрирует один назначенный интегратор.
- Исполнитель передаёт handoff с diff/коммитом, проверками и нерешёнными проблемами.
- Коммит доказывает изменения, а не работоспособность; после интеграции повторить затронутые проверки.

## Завершение

1. Проверить diff и исполнить обязательные доступные проверки.
2. Записать точные результаты, ошибки и UNVERIFIED; не скрывать ограничения среды.
3. Обновить TASK, каноническую строку и статус этапа.
4. Обновить PROJECT_STATE и CHANGELOG; ROADMAP — при изменении фокуса/статуса/прогресса.
5. Проверить `python3 scripts/check_development_docs.py`.
6. Передать handoff: SHA, изменённые файлы, команды, остаточные риски, следующая задача.
7. Не утверждать push/релиз без подтверждённого результата операции.
